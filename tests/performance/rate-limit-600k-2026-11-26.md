# Rate-limit contention on the representative catalog

On 2026-11-26 the release-profile production `AuthStore::record_rate_limit_attempt`
was exercised against an invocation-owned PostgreSQL fixture containing 35,000
artists, 50,000 releases and 600,000 tracks. The catalog was not read by the
rate-limit query. A small-fixture smoke preceded this run; the fixture was
removed afterward. The [raw results](rate-limit-600k-2026-11-26.log) contain
all 18 scenario samples and their exact counts. Three rounds ran sequentially
for each combination of one, eight or 32 workers and shared or separate actor
keys; each worker made 20 attempts. There were no returned errors, and the
number of retained keys and total attempts were checked after every case.

| Concurrent workers | Measured throughput across rounds and key patterns | p50 range | p99 range | Maximum sampled lock waiters |
|---:|---:|---:|---:|---:|
| 1 | 105–419 attempts/s | 2.4–5.9 ms | 2.6–65.1 ms | 0 |
| 8 | 243–330 attempts/s | 23.9–24.1 ms | 26.0–234.2 ms | 7 |
| 32 | 259–320 attempts/s | 95.9–98.2 ms | 206.0–307.9 ms | 31 |

The singleton PostgreSQL admission lock serializes attempts even for different
actor keys. The 5 ms `pg_stat_activity` samples are approximate and can miss
short waits. The measured function body was text-identical to the original
`a0979cde1fd2aeff5b8027d9d59336b678f1aa12` baseline. Checkout and hold
instrumentation was added after this measurement; this is not an independently
measured baseline/final comparison. The surrounding working tree was dirty. The release
test executable SHA-256 was
`bc033587bf5dd79056554520ee9c3ba168bb8c091ab55bb8014ff92b804d636c`;
the test and auth source SHA-256 values were respectively
`8784d779332431ea40fbc027727fa74d6685e85fdba19a285e905ce4547fa980` and
`1746dd298b0e32ee082a4b0052f3f693e904281fb12f7ef7019977ea8cb7569d`.
Hashes identify these files, not the complete transitive build inputs.

The test used the host and PostgreSQL settings described in the [mixed-load
baseline](db-competition-baseline-2026-11-26.md), with a maximum 40-connection
test pool, a two-thread Tokio runtime, and a separate one-connection sampler.
Cache state was uncontrolled. The first one-worker cases include cold-start
effects. No HTTP, password hashing, normal traffic distribution, mixed ingestion
or cross-process load was exercised. The test does not quantify expiry cleanup
or behavior near the global retained-key ceiling. These results identify a
contention bottleneck, but do not alone establish whether the current limiter is
adequate under representative authentication traffic or justify relaxing exact
multi-process admission, expiry, cleanup or capacity guarantees. That decision
remains open.
