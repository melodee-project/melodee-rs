# HTTP ingress contention diagnostic, 2026-11-26

The release server exercised the real HTTP/1 Jellyfin authentication,
direct-stream and playback-stopped paths on an invocation-owned PostgreSQL
fixture with 35,000 Artists, 50,000 Releases and 600,000 Tracks. An additional
valid 480-second MP3 was generated and ingested by the server. For each
connection limit, one authenticated idle keep-alive and one slow stream stayed
open while 16 stopped requests and 16 authenticated `/System/Info` requests
were issued. A transaction held the synthetic Track row lock for three seconds.
The client requested a 4,096-byte socket receive buffer and consumed stream
data slowly; the stream was deliberately closed before completion.

The table gives the nearest-rank p95 of each set of **16** requests. With this
sample count p95 and p99 are both the largest observed sample; they are not
stable estimates of production tail latency.

| HTTP connection limit | Stopped requests persisted | System-info requests completed during lock | Stopped p95 | System-info p95 | Server peak RSS |
| --- | ---: | ---: | ---: | ---: | ---: |
| 0 (disabled) | 16 / 16 | 16 / 16 | 3.248051 s | 0.004050 s | 33,284 KiB |
| 4 | 16 / 16 | 0 / 16 | 3.146476 s | 3.131097 s | 31,056 KiB |
| 16 | 16 / 16 | 0 / 16 | 3.266653 s | 3.044132 s | 32,184 KiB |
| 32 | 16 / 16 | 16 / 16 | 3.247443 s | 0.002112 s | 32,920 KiB |
| 64 | 16 / 16 | 16 / 16 | 3.269451 s | 0.003809 s | 32,872 KiB |

Every stopped request returned HTTP 204, all 16 unique plays per case were
present in PostgreSQL, and the Track's recommendation popularity matched its
total committed plays after each case. No stopped request completed while the
Track was locked. All five streams returned HTTP 200; **time to response
headers**, not time to the first media byte, ranged from 0.004274 to 0.004614
seconds. The raw output's original `ttfb_seconds` field has been relabeled
`time_to_headers_seconds` in the [sanitized samples](./ingress-600k-2026-11-26.json)
to describe what was actually timed. The harness has since been corrected to
record the first media byte separately; see the [subsequent representative run](./ingress-ttfb-600k-2026-11-26.md).

This demonstrates that the tested limits of 4 and 16 delayed unrelated
requests during this particular contention. It does **not** establish that 32,
64, or any other limit is generally safe. The server is process-wide, so enough
idle, slow, or stalled connections can consume any finite cap. The measurement
used one machine, one sample per cap, loopback HTTP/1, a synthetic Track lock,
one idle connection and one slow stream. It had no external proxy, concurrent
ingestion or search rebuild, no real player or audible-underrun measurement,
and uncontrolled cache and request scheduling. The initial 600K fixture took
151.3 seconds to seed; its media lived on tmpfs. The 11,521,445-byte source was
synthetic and ingestion time is excluded from the scenario measurements.

The host had an AMD Ryzen 9 3900X (24 logical CPUs) and approximately 62.7 GiB
RAM. PostgreSQL 18.3 used 128 MiB `shared_buffers`, 4 MiB `work_mem` and 100
maximum connections. Server peak RSS and CPU samples include startup and
authentication but exclude child processes. Rust used the release profile.
The server binary SHA-256 was
`2b3149d7a28213fc12e427923c7523fd8e64bd36d3cc92250d271f4cc5fe7913`;
the observed Git HEAD was `08de08d50cb1be6e76c66000232dae257c1a2d2f` with a
dirty working tree. The exact binary source state was not independently
established, and this is not a clean final-commit benchmark.

Reproduce after building the debug migration CLI and the release server:

```text
CARGO_BUILD_JOBS=2 RUST_TEST_THREADS=1 cargo build --locked --release -p melodee-server --bin melodee-server
python3 scripts/perf_representative.py -- python3 scripts/perf_ingress_workload.py --connection-limit 0 --connection-limit 4 --connection-limit 16 --connection-limit 32 --connection-limit 64 --plays 16 --probes 16 --hold-seconds 3 --media-seconds 480 --idle-connections 1
```

The workload verifies the fixture-owned database identity and sends requests
only to the actual loopback port reported by its own child server. The input
file, listener, database, tokens and log files are temporary and owned by the
invocation. The command above now also records first-media-byte timing; those
new observations are reported in the subsequent run and differ from the header-only times reported here.
