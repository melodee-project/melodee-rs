### Findings raised by this run

**F1 — a tagged release date never reaches the Release (9 fixtures).**
Every fixture carries a full `date` tag (`2019-04-12`, …) which the inspection stage records on each
Track (`files[].metadata.raw.date`), yet `releases.release_date` and `release_date_text` stay empty.
Cause: `ManifestReleaseObservation.date` is hard-coded `None` in the media observer
(`crates/melodee-media/src/lib.rs`, the `ReleaseManifest::new` call), so
`parse_observed_date(manifest.release_observation.date)` in the importer always receives `None`.
The only path that populates a release date is a `.blackbeard.provenance.json` sidecar, and it
supplies `release_date_text` only (a year). Status: **fixed after this run** — the observer now selects
the date tag carried by the most audio tracks (ties break towards the smallest value, so identical
corpora seal identical manifests) and passes it as `ManifestReleaseObservation.date`
(`select_release_date`, `crates/melodee-media/src/lib.rs`). Re-verified in `RUN-m2.md`; the assertion
is now a hard check rather than a gap.

**F2 — imported and provider cover art is never served (all fixtures, and every Release).**
`GET /images/release_<id>/original` answers `200` with a **zero-byte body** for both a Release whose
published bundle contains `artwork/<hash>.jpg` and a Release with a `catalog_provider_images` row.
`canonical_artwork_bytes` was never reached: the probe used `/images/album_<id>/original`, and the
size parser (`image_size` in `apps/melodee-server/src/native/images.rs`) only knew `thumbnail`,
`small`, `medium`, `large`, and numeric sizes, so an unrecognized token fell through to `empty_ok()` —
a silent `200` with no body and no content type. Status: **fixed after this run** — `original`/`source`
now serve the untransformed publication asset, and the resolver records which source produced a
response. Chasing it also exposed a second, real defect: provider artwork was consulted *before* the
published plan (contradicting ADR-0143 §2 and the function's own doc comment) and was logged as an
"operator override". Precedence is now override → published plan → provider → captured placeholder.
Re-verified in `RUN-m2.md`.

**F3 — History opened on an empty filter.**
`HistoryScreen` ordered its terminal states alphabetically, so it defaulted to `cataloged` — a state a
healthy catalogue has already left — and showed an empty table next to a full queue. **Fixed** in this
run (defaults to `indexed`, the successful terminal state); the corpus suite now asserts History lists
every finished fixture with the `Active` phase.

**F4 — a 35 % truncated MP3 still catalogues.**
Fixture 09 (truncated to 35 %) reached `indexed`: MP3 frame resilience makes truncation alone
survivable. Recorded as observed behaviour rather than a defect; the positive fault case is fixture 11.

**F5 — a Release with no album tag is correctly refused, not guessed.**
Fixture 11 (no `album`/`album_artist` tags, no sidecar) routed to `needs_review` with
`state_reason = validation.needs_review`, and produced no Release row. Correct behaviour, now pinned.

### Findings surfaced by the *harness* itself (product behaviour, working as designed)

- Sign-in is rate limited: a suite that logs in per test receives `429`. Fixed by authenticating
  once and persisting the Playwright storage state.
- OpenSubsonic token auth (`t`/`s`) validates against the stored **user secret**, not the password, so
  clients configured with `md5(password+salt)` fail with error 40; the password branch (`p`) works.
  Verified: `stream` returns `audio/mpeg` bytes over the network.
