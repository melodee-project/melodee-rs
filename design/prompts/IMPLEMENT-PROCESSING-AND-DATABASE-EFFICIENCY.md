## 1. Schedule only actionable provider work

1. Share the definition of provider eligibility across the capability endpoint, importer, backfill and worker. An external provider is eligible when enabled in effective settings and all required credentials are present. Preserve settings precedence, blank-secret handling and the local MusicBrainz option. Built-in Melodee search remains available interactively and creates zero background jobs. Unreachable providers, HTTP 429s and timeouts use the existing retry policy.
2. Maintain a small, revisioned PostgreSQL record of effective eligibility per external provider. Store booleans, never credentials. Refresh at startup, on relevant settings changes and through reconciliation at least once per minute. CLI and server imports use the same installation state. A resolver error retains the last known state and exposes a diagnostic. For a new installation with unknown eligibility, allow imports to become playable and catch up once the state is known. Pausing the enrichment worker pauses execution without forgetting eligible work.
3. Within the catalog transaction, deduplicate the affected Artist and Release IDs, join to eligible providers and insert the existing metadata and artwork purposes using set-based SQL. The number of scheduling SQL statements per import must be bounded independently of the number of Artists or providers. Keep network I/O, per-entity capability resolution and catalog scans off this path. Preserve current task uniqueness, transaction rollback and administrator artwork precedence.
4. On transition to eligible, create one durable backfill per provider revision. Scan live Artists and Releases by stable keyset in pages of 250. Advance each cursor in the transaction that enqueues its page. Reconcile missing purposes using the same scheduling keys. Genuine success and cache hits satisfy prior work. A historical success whose only outcome was `disabled` does not. Preserve exhausted genuine failures for diagnosis and explicit retry. Coordinate imports and provider-state changes so an import committing behind the cursor is still covered. Disabling fences an in-progress backfill. Repeated startups, unchanged settings and concurrent reconcilers must not restart a completed scan or duplicate work.
5. Reconcile the installed backlog in bounded transactions. Remove an ineligible provider's never-attempted queued row only after verifying zero attempts, zero dependent evidence and no lease. Add a dormant state for historically attempted work suspended by disablement, including disabled-only legacy successes. Preserve task IDs, append-only attempts, genuine retry budgets, unique attempt numbering, failures, merge evidence and real successes. Exclude dormant rows from runnable counts and claims. On enable, make unfinished dormant work runnable exactly once. Reclaim expired leases through existing fencing. Recheck the provider revision before dispatch. A disable observed before I/O releases the claim without generating a disabled attempt. Allow an in-flight request to finish under existing lease and override checks.
6. Resolve capabilities once per worker batch and reuse process-wide and per-provider concurrency controls. Drain another bounded batch promptly when the previous batch was full. Retain backoff, cancellation, rate limits and idle polling. Limit the claim index to runnable/recoverable states, including running jobs with expired leases. Preserve the scheduling uniqueness and entity lookup needed by merge operations. Keep genuine attempt history under ADR-0162. The long-term invariant is one scheduling key per distinct eligible entity/provider/purpose, regardless of repeated imports and settings refreshes.

**Acceptance.** For one new Artist and one new Release, with three of nine providers eligible for both purposes, import creates exactly **12** jobs. With zero eligible providers the same import creates **zero** jobs, attempts and external calls and reaches playable. A repeated import creates zero additional jobs. Enabling a fourth provider backfills exactly four missing jobs for those entities. Test credentials added/removed, disable/enable races, disabled-only historical success, genuine retries and terminal failures, active/expired leases, resolver failure, restart mid-page, two reconcilers, concurrent import, and Artist merge. A second backlog reconciliation changes zero settled rows.

**Capacity check.** On the disposable installation, submit 165 Releases evenly over 30 minutes (330/hour), each with one new Artist, three eligible providers, both purposes, a controlled 100 ms successful lookup and small synthetic artwork. Start with an empty queue and record arrivals, successful completions and oldest eligible age every minute. All 1,980 logical jobs must finish within five minutes of the final submission with configured concurrency limits respected. Separately simulate one provider returning 429s to prove healthy providers still make progress, genuine retries remain visible and Releases become playable. Publish the service rate required by the fixture alongside the measured rate. State explicitly when real provider quotas would limit catch-up.

## 2. Put full manifest evidence on persistent file storage

1. Store the full versioned manifest as an immutable evidence object under the configured `MELODEE__STORAGE__ASSET_ROOT`. Reuse the installation binding, content-addressed publication and SHA-256/length verification in ADR-0210. Keep the logical manifest row, ID, work-item association, version, existing semantic/sealed hashes, verified object reference and compact query facts in PostgreSQL. Preserve the existing on-disk publication bundle. Verify the physical asset digest and each existing Melodee hash against its own input and algorithm.
2. Preserve complete Blackbeard provenance documents, raw fallback text, lyrics, parsed sidecars and full Chromaprint strings in file storage. For new sidecars, retain original bytes from the existing bounded, hash-verified read, including non-UTF-8 encodings. For historical JSONB, preserve all existing fields and logical values, including unknown fields. Where only parsed JSON or decoded text survives, record its provenance as such. Upgrade without reading old staging, rereading audio or recomputing fingerprints. Use versioned, deterministic serialization and round-trip fixtures. For allowed pre-seal changes, atomically replace the reference after verifying the expected prior revision/hash. Preserve sealed manifest and overlay identities.
3. The asset receipt and reader currently limit individual objects to **10 MiB**. Preserve existing upload limits and support larger valid evidence. For evidence exceeding 10 MiB, stream fixed **4 MiB chunks** into the same store. Use an ordered, versioned descriptor on disk containing chunk references and the overall SHA-256 and length. Bound memory, handle descriptors in bounded reads and verify reconstruction. Register ownership of every part so shared objects survive deletion of one owner. Reuse objects on retry. Include original sidecars and descriptors in backup and hard-delete reference accounting. Apply the store's documented retention policy to superseded references and report their filesystem cost.
4. Replace direct SQL traversal of `manifest_payload` in every reader and writer. Inventory application code, CLI, scripts and diagnostics in closeout. Keep indexed relational facts for policy/classification, corrupt-file flags, external IDs, Track source/segment associations, audio technical fields and exact-match fingerprint digests. Preserve current BLAKE3 equality and CUE-derived Track semantics. Store bounded references for large lyrics and evidence values. Read those files only for authorized detail requests that require them. Keep browse, search, routine policy batches and Admin listings free of per-Track full-manifest reads. Verify files before binding references, and use short SQL write transactions with expected revision checks. Preserve Native and OpenSubsonic field values, null handling and precedence.
5. Implement an expand, backfill, verify and finalize upgrade via the normal migrator and `melodee-cli`. Supply read-only preflight and resumable status/verification commands. Report row and byte counts, bound store identity, missing prerequisites and peak database/filesystem headroom. Document stopping old writers. Backfill in stable ID order with at most 50 manifests per checkpoint and one large manifest in flight per migrator. Verify each file from its final path before committing its reference and progress. Run an **independent verification over every legacy row** comparing reconstructed JSON, hashes, references and derived query facts to the old source. Fence writers and revalidate before removing any inline evidence. A populated SQL-only upgrade lacking verified receipts must fail closed. A clean install and repeat startup after completion must skip bulk work.
6. Extend the storage guard with synthetic payload markers. Inspect actual persisted values after ingestion, import and migration, including fallback/error paths. Catch payloads reintroduced in text, arbitrary JSON, base64, arrays, caches or diagnostics touched by this feature. Preserve permitted cryptographic metadata. Separately measure logical bytes removed, physical table/TOAST/index sizes, deduplicated filesystem bytes, temporary allocation and WAL.

**Acceptance.** Upgrade fixtures for every supported manifest version and lifecycle, including active normalization, pre-catalog review, failed work and sealed imports. Include valid/invalid Blackbeard JSON, unknown fields, non-ASCII lyrics, CUE segments, shared evidence and a manifest over 10 MiB. Compare results for review edits, publication recovery, catalog import, novelty, Native Track details/lyrics and OpenSubsonic bit depth. Count file reads on hot paths. Exercise wrong store identity, missing or corrupt file, full disk, crash before and after SQL binding, interrupted finalization and concurrent migrators. Verify that failure preserves the recoverable source and that a retry converges. Rehearse a restore of the paired database and file store.

## 3. Bound processed search outbox history

1. Retain successful event detail for **7 days** by default, measured from `processed_at` in UTC. Add the ordinary Admin-editable setting `MELODEE__SEARCH__PROCESSED_OUTBOX_RETENTION_DAYS`, range 2–90. Preserve pending, leased, retryable and permanently failed rows. Retain exact hourly totals for **400 days** at one row per projection and UTC hour.
2. Calculate the chart's existing **distinct Track IDs successfully indexed per hour**. Two revisions in one hour count once. One Track indexed in two hours counts once in each. Preserve the live partial hour, the rolling 24-hour window including its partial first hour, zero-filled hours and the Admin API shape. Finalize a closed hour from the full raw hour before any portion is pruned. Coordinate finalization with acknowledgements so late commits cannot lose counts. Make the aggregate, finalization marker and partial-prune recovery idempotent. Serve sub-hour boundaries for the existing chart from recent detail. Backfill complete historical hours still available. Record the earliest trustworthy coverage in maintenance diagnostics.
3. Coordinate pruning with checkpoint and rebuild registration, snapshot, catch-up and activation. Pause pruning for a projection while it has a requested or resumable nonterminal rebuild. Serialize that decision with new rebuild registration. Require durable acknowledgement, a finalized hour, elapsed retention and a safe checkpoint before deleting each row. Persist a highest-pruned ID **per projection** atomically with pruning. Update every high-water reader to account for that value when raw rows disappear. Preserve correctness with ID gaps, out-of-order commits and failed low IDs. A maximum observed ID alone cannot prove every lower event was applied. Preserve tombstones, revision fencing and producer idempotency when an old unique outbox row has been pruned. Tantivy commit must continue to precede SQL acknowledgement.
4. Run maintenance hourly in bounded, cancellable passes of at most **1,000 ordered rows per transaction**. Yield between batches, use indexed selection and one maintenance owner per projection. Expose an operator dry run showing eligible, protected and failed counts, oldest retained completion, last finalized hour, last prune result and any blocking rebuild. Leave protected rows in place and report the reason when safe pruning cannot proceed.

Keep the finalized-through watermark after hourly aggregates age out. If a protected rebuild later releases detail older than 400 days, use the same acknowledgement and replay checks to clean it up without resurrecting expired chart buckets. Bound duplicate suppression by entity/revision, including existing deletion tombstones. Avoid moving one permanent record per event into another table.

**Acceptance.** Seed 100,000 eligible old successes plus recent, leased, pending, retryable and failed controls. Prune all and only the eligible rows. Compare buckets to an independent pre-prune distinct-count query. Run maintenance twice, interrupt a partial prune and resume. Test two workers, acknowledgements crossing UTC midnight, concurrent and interrupted rebuilds, pruning through an empty raw table, the next import and stale upsert replay after deletion. Rebuild with zero canonical media reads and compare documents, revisions, queries and generation counts against a control retaining its full outbox.
